# CubeTrace: one-night interview preparation

Your strongest story is the progression **BFS → bidirectional BFS → IDDFS → IDA*
→ admissible lower bounds → pattern databases → optimal full-cube search**.
Understand why each step exists. You do not need to memorize large tables.

## A. The 30-second explanation

“I modeled the Rubik's Cube as a graph where a state is a vertex and every face
turn costs one. I implemented BFS, bidirectional BFS and IDDFS to understand the
time-memory tradeoff, then used IDA* as the main solver. Its heuristic is the
maximum of three exact pattern database distances generated by reverse BFS.
Those distances never overestimate, so completed IDA* searches return globally
shortest solutions. I verify every returned path and cross-check shallow lengths
against BFS.”

## B. The 60-second explanation

“My project finds a shortest solution to a 3×3 cube under the face-turn metric:
R, R-prime and R2 each cost one. I represent pieces directly using corner and
edge permutation and orientation arrays.

“BFS proves the shortest-path idea but stores too many states. Bidirectional BFS
reduces the depth explored, yet remains memory-heavy. IDDFS keeps only a path
but repeats a lot of work. IDA* adds a lower bound h and searches with increasing
thresholds on g+h.

“I precompute exact distances for all corners and two five-edge subsets using
reverse BFS. Compact coordinates let me store these in byte arrays. I take their
maximum because one move can help several patterns at once; adding them would
risk overestimating. With an admissible heuristic and safe move pruning, the first
completed result is globally optimal. The tests compare it with BFS on 444
shallow cases. Hard inputs can hit a resource limit; I never relabel an approximate
solution as optimal.”

## C. The 2-minute explanation

“The cube is a unit-cost graph: a complete cubie configuration is a vertex, and
one of 18 face turns is an edge. The objective is minimum FTM length. In this
metric a half-turn counts as one, so quarter-turn-optimal and face-turn-optimal
are different problems.

“I began with BFS using a queue, visited map and parent pointers. It explores
in increasing depth, so its first solution is shortest. The weakness is exponential
memory. Bidirectional BFS searches from both ends and expands full layers,
preferably the smaller frontier. That roughly halves the depth, but both visited
sets still grow quickly. IDDFS combines optimal depth with DFS path memory,
although it repeatedly expands shallow nodes.

“The main solver is IDA*. It starts with bound h(start). DFS prunes a node if
g+h exceeds that bound. If an iteration fails, it returns the smallest exceeded
f-value as the next bound. I use no two-phase restriction or transposition table.

“For h, I build exact pattern databases with reverse BFS from solved abstract
states. One stores all eight corners including twist; two store five labeled
edges each, including their positions and flips. Any full solution must solve
each abstraction, so their distances are lower bounds. Their maximum remains
a lower bound; their sum could double-count the effect of a turn.

“The corner coordinate combines an 8! permutation rank and a base-three twist
rank with 3^7 possibilities. Edge coordinates use ordered positions of selected
pieces and five flip bits. Primitive arrays keep the three distance payloads to
about 90 MiB, with about 11 MiB more for move tables. Databases cache to disk.

“Optimality follows because every prefix of an optimal path has g+h at most its
total optimal length. The threshold cannot jump past that length, and the safe
pruning preserves a shortest representative. Every returned solution is replayed
on the full cube. I also checked shallow lengths against BFS and compared cubie
moves to an independent sticker model. A measured 12-turn case solved in 225 ms,
but a 14-turn case hit 100 million nodes. I claim optimal completed results,
not fast solves for all random cubes.”

## D. Complete solving flow

```text
scramble text, e.g. R U F
    ↓ CubeParser.parseMoves
18-move notation, every move costs 1
    ↓ apply moves to CubeState.solved()
immutable full cubie state
    ↓ encode once
corner coordinate + edge-A coordinate + edge-B coordinate
    ↓ PDB array lookups
h = max(corners, edgesA, edgesB)
    ↓ OptimalSolver.solve
bound = h(start)
    ↓ depth-first search
g+h > bound? return this exceeded f
full cube solved? preserve path and return FOUND
otherwise explore allowed face turns; update cube and coordinates
    ↓ if no solution
raise bound to the smallest exceeded f; repeat
    ↓ if FOUND
replay solution on the ORIGINAL full CubeState
    ↓
verified minimum-length FTM solution + metrics
```

A limit propagates out immediately, discards the partial path and reports
`Search limit reached`. It makes no claim that the cube is unsolvable.

## E. Why My Solver Is Optimal

Say this first:

“IDA* searches in increasing f-cost bounds. Since every move costs one and my
heuristic never overestimates the remaining distance, IDA* cannot skip a shorter
solution. Therefore the first solution it finds is globally optimal under FTM.”

Then explain the important detail. Let the optimum be C*. On any shortest path,
`g+h <= C*` at every prefix. The initial bound is at most C*. Whenever a smaller
bound fails, the first cutoff on that optimal path has f<=C*, so the minimum
exceeded f cannot jump over C*. At bound C*, an optimal representative survives
all pruning and complete DFS reaches it. Accepted goals have `h=0` and `g<=bound`.
Thus the first solution has length C*.

Required assumptions: correct moves/coordinates, exact compatible cached data,
admissible nonnegative h, all 18 unit-cost moves, the full goal test, completeness
within a threshold, safe move pruning, and no interrupted search. Consistency
also holds for these exact unit-cost abstraction distances, but admissibility
is the essential property for this IDA* optimality argument. Verification proves
the path works; it does not by itself prove shortestness.

## G. Top 40 interview questions

1. **Why model a cube as a graph?** A state is a vertex; a legal turn is an edge.
   Solving becomes a shortest-path problem with standard search algorithms.

2. **Does BFS guarantee shortest? Why?** Yes here: all edges cost one. It discovers
   states in increasing number of moves. With unequal costs, plain BFS is not enough.

3. **Why not use BFS for the main solver?** Both frontier and visited/parent maps
   grow exponentially with depth. O(b^d) memory becomes the practical limit.

4. **Why bidirectional BFS?** If both endpoints are known and reverse moves are
   available, two searches to roughly d/2 can do much less work than one to d.
   They still consume exponential memory.

5. **How does your bidirectional reconstruction work?** Follow parents from meeting
   to input, then reverse that list. Append the inverse of the path from solved
   to meeting. Inverse means reversing order as well as inverting individual moves.

6. **Can you safely expand the smaller frontier?** Yes, at full-layer boundaries.
   Each side's visited map is a complete distance ball. If radii a and b have not
   met, no path of length <=a+b exists. First contact after one full-layer extension
   gives the next possible distance. Arbitrary vertex-by-vertex switching needs
   a more careful termination rule.

7. **Why IDDFS?** It gets BFS-like optimal depth using DFS-like active-path memory
   by searching depth limits 0,1,2,... . The cost is repeated shallow expansion.

8. **IDDFS versus IDA*?** IDDFS limits g, the moves taken. IDA* limits g+h, an
   estimated total solution cost, using a lower bound to prune more branches.

9. **Why IDA*?** It combines optimal search with small DFS path memory and can use
   strong pattern database lower bounds. It trades repeated work for memory.

10. **Why not A*? Why does it use too much memory?** A* keeps a global priority
    queue of candidates and usually a best-cost/closed map. Those structures can
    dominate memory in an enormous state graph. IDA* keeps the active DFS path.

11. **What are g, h and f?** g is moves used, h is a lower bound on moves left,
    and f=g+h is a lower bound on the cost of a solution extending that path.

12. **What is an admissible heuristic?** It never exceeds true remaining distance.
    An estimate of 5 means at least 5 moves remain, not that exactly 5 remain.

13. **What if the heuristic overestimates?** A shorter solution path can be cut off
    while a longer one is accepted. The global optimality guarantee is lost.

14. **Why pattern databases?** They spend preprocessing and memory to obtain cheap,
    informative lower bounds at millions of full-search nodes.

15. **How do you generate a PDB, and why BFS?** Forget unselected pieces, start at
    abstract solved, and BFS the unit-cost abstract graph. Each first discovery
    stores that abstraction's exact shortest distance.

16. **Why reverse BFS?** We need distance to the abstract goal from every abstract
    state. Because every move's inverse is available, outward BFS from the goal
    computes those distances for this undirected graph.

17. **Why is a PDB distance a lower bound?** Any complete solution also solves the
    selected pieces. Ignoring constraints cannot require more moves than solving
    all constraints, so the abstract minimum cannot exceed the full minimum.

18. **Why max of multiple databases? Why not sum?** Each bound is individually safe;
    max stays safe. One turn can improve corners and both edge patterns together.
    Sum could charge three times for that same turn. Disjoint pieces alone do not
    make heuristics additive; that requires justified cost partitioning.

19. **How is the cube represented?** Four private arrays: corner permutation and
    twist, edge permutation and flip. Entry i describes the piece/orientation at
    position i. Moves use fixed source-position and orientation-delta tables.

20. **What is permutation?** Which labeled piece occupies each position. Identity
    permutation means every piece is in its own position, regardless of orientation.

21. **What is orientation?** A corner has three twists, an edge two flips. A piece
    can be in the correct position while facing the wrong way. Both must be solved.

22. **Why only seven independent corner twists?** Legal turns preserve total corner
    twist modulo three. Once seven twists are known, the eighth must make the sum
    zero modulo three. Thus 3^7, rather than 3^8, possibilities.

23. **How does coordinate encoding work?** Rank the permutation, encode orientation
    as base-three/base-two digits, then combine the independent components using
    `permutationRank * orientationCount + orientationRank`.

24. **What is Lehmer code?** Count smaller remaining labels to the right at each
    position. Those mixed-radix digits uniquely rank a permutation. Decoding chooses
    unused labels in order. `[2,0,1]` has rank 4 among the six three-piece permutations.

25. **How are edge subsets indexed?** Fix five piece identities and record each
    one's position in that identity order. The positions have 12P5 possibilities,
    encoding both subset location and selected-piece arrangement. Append five flip
    bits. No separate combination coordinate is needed.

26. **Why primitive arrays?** Dense integer indexes need no object keys or hashing.
    A byte per distance has much less overhead than millions of boxed entries.
    -1 marks undiscovered; the builder checks overflow. Observed maxima were 11/9/9.

27. **What is the branching factor?** There are 18 possible moves before pruning.
    Same-face and opposite-face rules lower the effective branching. It is still
    exponential search; do not call the branching factor a constant 18 after pruning.

28. **Which redundant moves are pruned?** Consecutive turns of the same face, and
    adjacent commuting opposite faces in the noncanonical order D-U, R-L or B-F.
    Immediate inverses are already covered by the same-face rule.

29. **Can pruning remove the optimal path? Why is yours safe?** Bad pruning can.
    A same-face pair shortens or cancels, so no shortest word needs it. Opposite
    faces commute, so swapping them preserves length and state. At least one
    canonical representative of every shortest solution remains.

30. **Why does IDA* find an optimal solution?** Each prefix of an optimal path has
    f<=C*. The threshold starts <=C* and the minimum-exceeded rule cannot jump
    past C*. Complete search at C* finds a shortest representative. See the proof.

31. **What metric defines optimality? Why is R2 one move?** FTM defines each turn
    of one face, including a half-turn, as one move. The graph explicitly has an
    R2 edge of cost one. In quarter-turn metric R2 would cost two instead.

32. **Does this use Kociemba's ordinary two-phase algorithm?** No for the main
    solver. Ordinary two-phase search prioritizes fast valid solutions and generally
    does not guarantee globally minimum FTM length. This code searches the full cube.

33. **How did you test optimality?** IDA* matched BFS lengths on 444 deterministic
    shallow cases. BFS is an independent shortest-path oracle at those depths.
    The algorithmic proof supplies the general guarantee; shallow tests catch bugs.

34. **How did you test correctness?** Move/inverse identities, sequence inverses,
    an independent geometric sticker oracle, coordinate roundtrips, table-transition
    comparisons, PDB checks, invalid-state rejection and full replay of every solution.

35. **What is the biggest performance bottleneck?** Exponential node growth on
    difficult inputs. Per-node work includes immutable cube allocation and table
    lookups. A good heuristic reduces nodes but does not eliminate exponential growth.

36. **What is the memory bottleneck?** The 84.095 MiB all-corner distance array for
    IDA*. The three PDBs and move tables total about 100.897 MiB of primitive payload.
    In basic BFS, the growing state/parent map becomes the main memory problem.

37. **What time-memory tradeoff do PDBs make?** Pay preprocessing, storage and
    loading time to reduce later search. Bigger patterns usually give stronger
    bounds, but increase preprocessing and memory. Smaller patterns preserve
    optimality while potentially slowing search dramatically.

38. **How would you improve it?** Larger/additional admissible patterns, compact
    four-bit distances, and careful in-place apply/undo could help. A transposition
    table needs a proof that its depth/path-context handling is safe. I deliberately
    skipped that complexity in this interview-sized version.

39. **What happens on a timeout or node cap? Can it solve arbitrary legal states?**
    The unrestricted finite search is complete and optimal, subject to its model
    and data assumptions. With practical caps, difficult states may not finish.
    It reports a search limit, returns no path and makes no impossibility claim.
    It is not a fast arbitrary-random-cube solver.

40. **Which optimizations did you choose, and does h=0 mean solved?** Primitive
    distances, compact coordinates, factorized move tables and proved move pruning.
    No: two edges are ignored by the PDBs. Both can be flipped while all patterns
    are solved. The full `CubeState.isSolved()` test is essential.

## The 10 code sections to know

1. `Move`: all 18 enum entries and `inverse(List<Move>)` — unit costs and path inversion.
2. `CubeState.apply` — position sources, twists mod 3, edge XOR, immutable child.
3. `CubeState.isSolved`, `equals`, `hashCode` — correct goal and graph state identity.
4. `BasicSolver.bfs` and `path` — FIFO queue, visited map, parent reconstruction.
5. `BasicSolver.bidirectionalBfs` — smaller full layer and goal-side path inversion.
6. `BasicSolver.iddfs` / `depthLimited` — outer increasing depth, inner DFS/backtracking.
7. `PatternDatabase.generate` — discover each abstract distance by exact BFS layers.
8. `Coordinates.encodeCorners` and `rankEdgePositions` — compact unique indexes.
9. `PatternDatabases.heuristic` and `Move.allowedAfter` — admissibility and safe pruning.
10. `OptimalSolver.solve` / `search`, followed by `Tracker.finish` — threshold,
    smallest exceeded f, recursive return signals, backtracking and final replay.

On paper, rewrite the IDA* loop and recursion without looking. Explain the three
return categories: FOUND, LIMIT, or minimum exceeded f. The three coordinates
carried with a cube are cached abstract state, not an extra phase or search rule.

## Claims you can defend

“Completed searches return globally minimum FTM length.” “I used full-cube IDA*
with admissible reverse-BFS pattern databases.” “I compared optimal lengths with
BFS on 444 shallow cases.” “I replay every returned path.” “A measured 12-turn
case finished optimally in 12 moves.” Read `MEASUREMENTS.md` for timing context.

Do not say “all random cubes solve instantly,” “12 scramble moves always require
12 solution moves,” “disjoint PDBs can always be added,” “IDA* uses almost no total
memory,” “testing proves optimality for all cubes,” or “a search limit means no
solution exists.” Do not claim you memorized every coordinate implementation.
